Звіт з лабораторної роботи №11

Тема: Document Processor: шаблонні кроки й реалізації

Мета: Навчитися використовувати абстрактні класи для реалізації патерну Template Method, створювати загальну логіку обробки в базовому класі та специфічну логіку в похідних класах.

1. Короткий опис реалізованої системи (Варіант 6)

У ході виконання роботи було реалізовано систему запуску тестів TestRunner на основі патерну Template Method:

* Абстрактний базовий клас TestRunner визначає каркас алгоритму запуску тестів у методі Run():

* SetUp() — підготовка тестового середовища (abstract)

* ExecuteTests() — виконання тестів (abstract)

* CollectResults() — збір та вивід результатів (virtual)

* TearDown() — очищення ресурсів (virtual)

* GenerateReport() — формування підсумкового звіту (abstract)

* Похідні класи:
* UnitTestRunner — реалізує підготовку моків та вивід звіту для модульних тестів

* IntegrationTestRunner — перевизначає підключення до бази даних та скидання її стану після виконання

* E2ETestRunner — реалізує запуск браузера для тестування інтерфейсу

Всі об'єкти обробляються поліморфно через колекцію базового типу List[cite: 22].

3. Відповіді на контрольні запитання

1. Що таке патерн Template Method і для чого він використовується?
Template Method — це поведінковий патерн, який визначає скелет алгоритму в базовому класі, дозволяючи похідним класам перевизначати окремі кроки без зміни загальної структури алгоритму.


2. Яка різниця між абстрактними та віртуальними методами в контексті цього патерну?
Абстрактні методи (abstract) не мають реалізації в базовому класі та є обов’язковими для реалізації в похідних класах. Віртуальні методи (virtual) надають базову реалізацію за замовчуванням і перевизначаються лише за потреби.


3. Які переваги дає винесення спільної логіки в базовий клас?
Усувається дублювання коду (принцип DRY), гарантується чітка послідовність виконання кроків та спрощується подальше обслуговування системи.


4. Коли доцільно використовувати Template Method замість інтерфейсів?
Коли є зафіксований алгоритм із послідовними кроками, частина з яких є спільною для всіх реалізацій. Інтерфейси описують лише контракт і не можуть зафіксувати порядок виконання чи містити спільну логіку[cite: 13, 20].


5. Наведіть приклад з реального життя, де застосовується цей патерн.
Приготування напоїв у кавовому автоматі (кип'ятіння води, заварювання, наливання, добавки) або пайплайни деплою коду (Build, Test, Package, Deploy)[cite: 20, 22].
